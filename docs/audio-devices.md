# Audio devices (Settings → Connectivity)

The **Audio devices** card below the robot connection cards lets the user
choose the robot's microphone and speaker independently. Flutter only stores
the *desired* device. A device is shown as active only after the backend
confirms it.

## What exists on the Jetson today

From `unitree_g1/medza` (read-only review):

| Setting | Values | Effect |
|---|---|---|
| `AUDIO_INPUT_TARGET` | `robot` / `local` | `robot` uses the G1 microphone array (UDP multicast `239.168.123.161`); `local` uses `arecord` |
| `AUDIO_INPUT_DEVICE` | ALSA name, e.g. `plughw:CARD=…,DEV=0` | Local microphone, e.g. a USB microphone |
| `AUDIO_OUTPUT_TARGET` | `robot` / `local` | `robot` uses the G1 speaker through the Unitree Audio SDK; `local` uses ALSA `aplay` |
| `AUDIO_OUTPUT_DEVICE` | ALSA name | Local speaker. `resolve_local_output_device` waits for it to appear |

These are read from the environment **once, at process start**. There is no
runtime device discovery or switching, and no WebSocket message for audio
devices. The Jetson WebSocket server (`apps/telemetry_ws.py`) is not in this
checkout, so its message handling could not be verified.

## Flutter side

- `lib/features/settings/data/audio_device_backend.dart`
  - `AudioDeviceBackend` interface and `AudioDevice`.
  - **Device IDs are opaque.** They are generated by the server (`robot:mic`,
    `robot:speaker`, `system:default`, `usb:<vid>:<pid>:<port-path>`), and
    Flutter stores and sends them unchanged. It never parses them or derives
    meaning from them.
  - `MockAudioDeviceBackend`: Demo Mode only. Simulated devices, labeled
    "(simulated)". It never records, plays, or sends anything.
  - `UnavailableAudioDeviceBackend`: live mode. It sends nothing and reports
    that device management is not available yet.
- `lib/features/settings/data/audio_device_protocol.dart`: a **provisional**
  v1 codec (`audio_get_devices`, `audio_get_settings`, `audio_set_settings`,
  `audio_test_input`, `audio_test_output`). It is isolated on purpose: no
  app code imports it and nothing is sent. Replace it once the Jetson API
  contract exists.
- `lib/features/settings/application/audio_devices_controller.dart`
  - Uses the app's existing Demo Mode (`voiceDemoModeProvider`).
  - Discovery runs silently on open. Only **Refresh devices** shows a
    notification.
  - Changes and tests are refused while a realtime conversation or TTS owns
    the audio session (`audioSessionProvider`).
  - Requests time out after 8 s. Tests are bounded (10 s), start only on
    click, and can be cancelled.
  - The desired IDs are stored in `SettingsState.audioInputDeviceId` and
    `SettingsState.audioOutputDeviceId`. This is the existing settings
    architecture, which is in memory until `SettingsPersistence` is bound.

## Needed on the Jetson for real selection

1. **Discovery:** with server-generated stable IDs (`robot:mic`,
   `robot:speaker`, `system:default`, `usb:<vid>:<pid>:<port-path>`), a
   display name, a direction, a kind and a `connected` flag. This is in
   progress on the backend.
2. **Runtime switching:** the audio service currently builds its recorder and
   output once. It needs a safe way to rebuild them, and must refuse while a
   conversation or TTS is active (`busy`).
3. **Bounded tests:**
   - Input: record a few seconds, then report the peak level and discard the
     audio.
   - Output: play a short, quiet tone at a capped volume.
   - Both must be cancellable.
4. **Protocol on the existing authenticated WebSocket:** versioned replies
   that carry `request_id`, plus error codes `unavailable`, `rejected`,
   `busy`, `not_found` and `timeout`. Advertise the capability first, so the
   app only enables live mode when the robot supports it.
5. **Persistence:** decide whether the choice survives a restart, either by
   writing to the runtime config or by keeping it session-only.

Once that exists:

- Implement a live `AudioDeviceBackend` that writes through the dashboard's
  channel.
- Route the reply frames in `DashboardController._handleTelemetry`.
- Return the live backend from `audioDeviceBackendProvider` when Demo Mode is
  off.
